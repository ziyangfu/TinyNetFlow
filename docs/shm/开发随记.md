memfd 是一个文件描述符（file descriptor），它本质上是一个整数，代表内核中的一个打开的文件或资源。文件描述符本身是进程本地的，不能直接通过普通的 send 或 write 函数发送给另一个进程。这是因为文件描述符在不同的进程中可能指向不同的资源，甚至相同的整数值在不同的进程中可能代表完全不同的文件。

为什么不能直接用 send 或 write 发送文件描述符？
文件描述符是进程本地的：每个进程都有自己的文件描述符表，文件描述符的值只在当前进程中有意义。例如，进程 A 中的文件描述符 3 和进程 B 中的文件描述符 3 可能指向完全不同的资源。

需要跨进程传递文件描述符：为了将一个文件描述符从一个进程传递到另一个进程，操作系统需要在内核层面进行特殊处理，确保目标进程能够正确引用相同的资源。

如何跨进程传递文件描述符？
在 Unix 系统中，跨进程传递文件描述符的标准方法是使用 sendmsg 和 recvmsg 系统调用。这些系统调用支持通过辅助数据（ancillary data）传递文件描述符。具体来说：

sendmsg：允许发送消息的同时，通过 SCM_RIGHTS 控制消息传递文件描述符。

recvmsg：允许接收消息的同时，通过 SCM_RIGHTS 控制消息接收文件描述符。

为什么必须使用 sendmsg 和 recvmsg？
辅助数据（Ancillary Data）：sendmsg 和 recvmsg 支持通过 struct msghdr 的 msg_control 字段传递控制信息（如文件描述符）。

内核支持：只有内核能够正确地将文件描述符从一个进程映射到另一个进程，并确保两个进程引用相同的资源。

是否可以用其他方法传递文件描述符？
除了 sendmsg 和 recvmsg，还有一些其他方法可以间接传递文件描述符，但这些方法通常更复杂或不推荐：

通过 /proc 文件系统：

在 Linux 中，可以通过 /proc/[pid]/fd/[fd] 访问其他进程的文件描述符。

这种方法需要目标进程的权限，并且不适用于所有场景。

通过 fork 和 exec：

父进程可以通过 fork 创建子进程，子进程会继承父进程的文件描述符。

这种方法只适用于父子进程之间的文件描述符传递。

通过 Unix Domain Socket 的 SCM_RIGHTS：

这是最标准、最推荐的方法，也是你的代码中使用的方法。

总结
send 和 write 不能直接发送文件描述符，因为它们只能发送普通数据，无法处理辅助数据。

sendmsg 和 recvmsg 是唯一的标准方法，用于通过 Unix Domain Socket 传递文件描述符。

如果你尝试用 send 或 write 发送文件描述符，实际上发送的是文件描述符的整数值，而不是文件描述符本身，这会导致目标进程无法正确使用该描述符。

因此，在你的代码中，使用 sendmsg 和 recvmsg 是正确的做法。
