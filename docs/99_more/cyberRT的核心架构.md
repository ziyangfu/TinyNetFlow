cyberRT为什么只使用了fastDDS的RTPS层，而不是整个fastDDS?

Cyber RT（Apollo Cyber Real-Time）选择仅使用 Fast DDS 的 **RTPS 层（Real-Time Publish-Subscribe Protocol）** 而非完整 Fast DDS 栈，主要基于以下核心设计考量：

------

### ⚙️ **1. 轻量化与性能优化**

- **RTPS 层是 Fast DDS 的通信核心**：RTPS 定义了数据分发的底层协议（如端点发现、消息序列化、传输控制），剥离了 DDS 层的复杂抽象（如 QoS 策略管理、全局数据空间模型），减少了中间件开销27。
- **降低延迟**：RTPS 直接通过 UDP/TCP/共享内存传输数据，避免了 DDS 层额外的封装解析，更适合自动驾驶场景的微秒级实时性要求34。
- **资源占用少**：RTPS 层代码更精简，适合嵌入式或资源受限的车载计算平台1。

------

### 🔧 **2. 自主可控的通信调度**

- **定制化通信模型**：Cyber RT 自研了基于协程的调度器（如 `CRoutine`），直接控制任务执行顺序和 CPU 核绑定。若引入完整 DDS 的线程模型，会与用户态调度冲突，降低实时性3。
- **零拷贝优化**：通过共享内存（SHM）传递数据指针，RTPS 层支持直接内存访问，而 DDS 层的序列化/反序列化可能引入复制开销78。
- **简化 QoS 管理**：完整 DDS 提供 20+ 种 QoS 策略（如历史缓存、持久化），但 Cyber RT 仅需可靠性、截止时间等核心策略，其余通过框架层实现（如通信通道的优先级调度）510。

------

### 🧩 **3. 模块化与灵活性**

- **解耦通信与计算**：Cyber RT 将 **通信协议**（RTPS）与 **任务调度**（Scheduler）分离。RTPS 仅负责数据传输，调度器独立管理协程生命周期，避免 DDS 线程模型侵入框架39。
- **热更新支持**：动态加载组件（`.so` 文件）时，RTPS 的轻量化设计减少符号冲突风险，而完整 DDS 的全局状态管理（如 DomainParticipant）会增大热替换复杂度13。
- **跨平台兼容**：RTPS 作为 OMG 标准协议，易于对接其他 DDS 实现（如 Cyclone DDS），提升框架适应性10。

------

### ⚡ **4. 实时性保障**

- **确定性延迟**：RTPS 层支持 **共享内存传输（SHM）** 和 **进程内交付**（Intra-process Delivery），同一进程的 Reader/Writer 直接回调，无网络栈延迟78。
- **规避 DDS 发现机制**：完整 DDS 的自动发现（PDP/EDP 阶段）依赖多播通信，在车载网络可能引发广播风暴。Cyber RT 改用静态配置拓扑（DAG 文件），直接指定通信关系39。

------

### 🔄 **5. 与现有架构深度集成**

- **统一数据模型**：Cyber RT 使用 Protobuf 定义消息格式，通过 RTPS 传输序列化后的二进制数据，而完整 DDS 的 IDL 工具链（如 Fast DDS-Gen）会增加构建复杂度15。
- **资源隔离需求**：Cyber RT 通过 `ClassLoader` 隔离不同模块，RTPS 层无全局状态，而 DDS 层的 DomainParticipant 可能引发跨模块冲突13。

------

### 💎 **总结：Cyber RT 的取舍逻辑**

| **完整 Fast DDS**          | **仅用 RTPS 层**               | **Cyber RT 的收益**              |
| :------------------------- | :----------------------------- | :------------------------------- |
| 提供全局数据空间模型       | 仅负责点对点通信               | 简化架构，避免冗余抽象层         |
| 自动发现节点（多播开销大） | 静态配置拓扑（DAG 文件）       | 降低网络负载，提升确定性         |
| 线程模型与调度策略强绑定   | 协程调度器自主控制任务生命周期 | 实现用户态调度，减少内核切换延迟 |
| 完整 QoS 策略链            | 仅需核心策略（可靠性/时效性）  | 降低配置复杂度，资源占用更少     |

这种设计使 Cyber RT 在 **通信效率**、**实时控制** 和 **动态扩展** 三者间取得平衡，成为自动驾驶高并发场景的更优解。未来若需增强 QoS 能力，可通过扩展 RTPS 配置实现，而非引入完整 DDS 栈
